## Context

R1.0 H5 基于 Next.js App Router，但业务主体仍是单个 Client Component：`WelcomePage` 以 `view` 切换欢迎/登录/协议/档案，`ProfileFlow` 再以 `profileSteps[index]` 切换建档、首页、每日指引、我的以及大量后续版本原型。该结构在原型期实现速度快，但现在形成三个约束：所有业务代码共享一个解析单元；URL、浏览器历史和刷新无法表达当前业务位置；认证、数据加载、返回目标和流程状态耦合在同一个组件。

测试环境继续采用 `next build` 静态导出、Nginx 静态文件服务和同源 `/api/v1` 反向代理。静态导出无法为任意运行时资源预生成动态路由，因此本设计必须使用可导出的固定业务路径，并将非敏感资源标识放在受校验的查询参数中。后端 OpenAPI、Session Cookie、内存 Access Token、幂等键、生成任务和账务语义均保持不变。

主要利益相关方包括 H5 用户、前端开发与测试、后端接口维护者和测试环境运维。迁移的首要约束是业务行为不回退，其次才是代码组织与性能收益。

## Goals / Non-Goals

**Goals:**

- 以真实 URL 表达欢迎、登录、今日、建档、每日指引、我的及核心详情页面，并支持直接打开、刷新、前进和后退。
- 以业务域作为代码、样式、数据和错误边界；访问公开首页时不加载受保护业务域实现。
- 保留连续流程的域内状态机，不为弹窗、生成中、确认、失败重试或每个表单步骤创建路由。
- 统一认证恢复、协议更新、受保护路由回退和安全 `next` 参数处理。
- 明确服务端数据、流程状态、URL 状态和临时敏感数据的所有权与恢复策略。
- 通过分阶段迁移、双路径兼容、自动化回归、性能预算和不可变发布目录实现安全上线与快速回滚。

**Non-Goals:**

- 不修改 `/api/v1`、OpenAPI、数据库模型、鉴权协议、账务或生成任务状态机。
- 不在本变更中开放 R1.1 问事、成长、关系、商城或订单能力。
- 不把 166 个逻辑状态全部转换为独立 URL，也不引入传统多页整页刷新。
- 不迁移到 Next.js 常驻服务端渲染部署；本阶段继续支持静态导出。
- 不以引入新的全局状态库或请求缓存库作为前置条件。

## Decisions

### 1. 使用固定业务路由，动态资源使用受校验查询参数

首批路由如下：

| 路由 | 职责 | 状态模型 |
| --- | --- | --- |
| `/` | 欢迎页与公开入口 | 页面状态 |
| `/login` | 手机号登录/注册 | 局部表单状态 |
| `/consent` | 必要协议更新确认 | 局部表单状态 + 安全 `next` |
| `/home` | 今日首页 | 服务端资源状态 |
| `/profile/create` | 本人建档 | 域内状态机 |
| `/daily` | 每日指引创建/生成流程 | 域内状态机 |
| `/daily/report?date=YYYY-MM-DD` | 已生成每日指引 | 可恢复资源状态 |
| `/my` | 我的首页 | 服务端资源状态 |
| `/my/profile` | 本人档案与初识入口 | 服务端资源状态 |
| `/my/seeds` | 智慧种子账户与明细 | 服务端资源状态 |
| `/my/reports` | 报告列表 | 服务端资源状态 |
| `/my/archive` | 人物档案库 | 服务端资源状态 |
| `/legal?documentId=...` | 协议阅读 | 公开资源状态 |

采用固定路由而非 `/daily/[date]`，是为了继续兼容静态导出并允许任意日期在运行时恢复。`date`、报告 ID、档案 ID等非敏感资源标识必须进行格式与所有权校验；出生日期、出生时间、手机号、验证码、Token 和完整问题文本不得进入 URL。

备选方案是迁移到 Next.js Server 部署并使用任意动态段，但会扩大部署面和运维风险，本次不采用。

### 2. 业务域路由，域内有限状态机

路由只表达可独立进入、刷新后可恢复、具有明确页面标题或业务资源边界的页面。建档内部的填写、确认、计算、初识和赠礼步骤仍由 `useReducer` 管理；每日指引内部的确认额度、生成中、失败重试和完成跳转同样由状态机管理。

状态机必须使用具名状态和显式事件，而不是继续依赖数组下标，例如：

```text
profile: editing → confirming → calculating → first-look → gift → complete
daily: start → confirming-cost → generating → ready | failed
```

这样既避免过度路由化，也消除 `setStep(14)` 这类不可读跳转。域内“返回”触发状态机事件；浏览器返回只负责退出当前业务域或返回上一核心路由。

备选方案是每个步骤一个 URL，虽然历史更细，但会暴露无意义中间状态、增加非法直达和恢复分支，因此不采用。

### 3. 薄路由页面与按域模块边界

`frontend/app/**/page.tsx` 只负责路由入口、Metadata、守卫组合和业务域根组件。实现移动到：

```text
frontend/src/features/auth/
frontend/src/features/home/
frontend/src/features/profile/
frontend/src/features/daily/
frontend/src/features/my/
frontend/src/shared/
```

全局 CSS 仅保留 reset、设计令牌、应用外壳和真正共享的基础组件样式；各业务域使用 CSS Modules 或域级样式入口。禁止由根布局静态导入所有业务域实现。构建测试必须检查 `/` 的初始资源清单不包含 profile、daily、my 的页面 chunk。

备选方案是仅增加 URL、仍复用单体 `page.tsx`，这不能解决首包解析和维护问题，因此不采用。

### 4. 统一 Session 与协议守卫

新增单例 `SessionProvider`/`useSession`，复用当前 API Client 的 refresh 去重能力，并维护 `unknown | anonymous | authenticated | consent-required` 状态。

- `/` 和 `/login` 立即渲染，不等待 refresh；后台恢复成功后使用 `router.replace()` 进入安全目标或 `/home`。
- 受保护路由在 `unknown` 时显示轻量路由骨架，不渲染敏感内容；确认匿名后 `replace('/login?next=...')`。
- 任意受保护请求触发 `CONSENT_REQUIRED` 时，保存经过白名单校验的当前路径并 `replace('/consent?next=...')`。
- 登录或同意协议成功后只允许跳转到内部白名单路径，拒绝协议、绝对 URL、双斜线和未知业务域，防止开放重定向。
- 登出必须清理内存 Token、共享缓存和临时流程数据，再 `replace('/')`。

### 5. 按状态类别确定所有权和恢复方式

| 状态类别 | 所有权 | 恢复方式 |
| --- | --- | --- |
| Session、协议状态 | `SessionProvider` | Refresh Cookie + `/me` |
| 首页、余额、报告、档案 | 后端事实 | 进入路由后按 API 获取，写操作后失效相关缓存 |
| 当前业务资源标识 | URL | 格式校验、所有权校验、无效时进入域级错误态 |
| 建档/生成步骤 | 域内 reducer | 后端任务/资源存在时恢复；纯 UI 步骤使用安全默认状态 |
| 未提交的出生资料草稿 | `sessionStorage` | 版本化、短时有效、仅当前标签页、确认/登出/过期后清除 |
| Token、验证码、手机号 | 内存 | 不写 URL、localStorage 或日志 |

草稿键必须带 schema version、创建时间和流程类型。恢复前进行结构校验；不兼容、过期或损坏时清除并回到安全起点。对于已创建的 preview revision、generation task 或 report，优先以服务端资源状态恢复，不重复执行扣费或生成命令。

初期使用轻量的域级 hooks 和内存去重缓存，不立即引入 TanStack Query。若实现阶段发现跨路由失效和并发请求复杂度超过自有实现范围，再以独立决策引入成熟库。

### 6. 规定导航与可访问性语义

- 用户主动进入新的核心业务页使用 `router.push()`。
- 登录完成、守卫重定向、协议确认完成和生成成功后的规范化跳转使用 `router.replace()`，避免返回到不可重放页面。
- 页面内返回优先使用安全来源路由；存在有效浏览器历史时可以 `router.back()`，直接打开链接时回退到域默认页。
- 每次路由完成后更新页面标题并将焦点移动到页面主标题；加载、错误和协议状态使用可访问的 live region。
- 不依赖 `history.length` 判断站内来源；导航时通过受控 `from` 状态或域默认路径决定回退。

### 7. 保持命令幂等和业务语义

路由迁移不得把读请求变成写请求，也不得因组件重挂载重复调用 preview、confirm、claim、createTodayInsight 或 generate。所有写操作继续通过 API Client 生成 `Idempotency-Key`，组件额外使用进行中锁和后端资源状态判断。

React Strict Mode、刷新、前进后退和快速双击都必须有回归用例。生成任务页离开后再进入时只查询现有 task/report，不自动创建新任务或重复预留智慧种子。

### 8. 性能预算与可观测性

- `/` 首次加载不得包含 protected domain 的业务 chunk，也不得恢复完整 CJK WebFont 请求。
- `/` 的现代浏览器 gzip JS+CSS 总量不得高于当前约 263 KB 基线；目标是在域拆分后进一步降低至少 25%。
- 每个首批业务域新增的首路由 gzip JavaScript 目标不超过 100 KB；超限必须在交接记录中解释并获得评审。
- 记录规范化 route ID、navigation source、守卫结果、资源恢复结果和错误码；不得记录敏感字段或原始报告内容。
- 自动化测试解析构建产物和 HTML 资源清单，防止无意重新聚合为单体首包。

### 9. 用适配层分阶段迁移而非一次重写

先提取纯组件、API hooks 和状态机，再建立新路由。迁移期间保留旧 `ProfileFlow` 作为未迁移域的适配器，但新路由不得反向依赖完整旧入口。每完成一个业务域，就从旧 `profileSteps` 白名单和条件渲染中删除对应分支，直到单体入口只剩兼容跳转后再移除。

每阶段必须是独立提交、独立测试、独立推送且可部署。不得在最后一次性提交所有页面迁移。

## Risks / Trade-offs

- [系统字体在不同平台存在细微字形差异] → 保留字体令牌和关键设备视觉回归，不以重新加载完整 CJK 字体换取像素级一致。
- [路由拆分后重复请求增加] → 使用域级请求去重、短期内存缓存和写后精确失效；以网络测试验证而不是预先引入重型全局状态。
- [老用户登录恢复出现欢迎页闪现] → 公开页保持可交互，恢复成功后 replace；受保护路由使用轻量骨架，不阻塞匿名用户。
- [浏览器返回进入不可重放的中间态] → 中间态不建路由，完成型跳转使用 replace，直接访问使用域默认回退。
- [刷新导致敏感草稿泄露] → 敏感字段不进 URL/localStorage，sessionStorage 草稿版本化、短时有效并在确认、登出和过期后清除。
- [组件重挂载造成重复扣费或任务] → 写命令幂等、前端进行中锁、服务端资源优先恢复，并覆盖 Strict Mode/双击/刷新测试。
- [静态导出无法支持任意动态段] → 使用固定静态路由和受校验查询参数；若未来迁移服务端部署，另立变更升级动态段。
- [迁移期间两套导航逻辑分叉] → 限定适配层生命周期，每迁移一个域立即删除旧分支，设置单体入口移除完成条件。
- [功能回归难以及时发现] → 建立路由契约矩阵、关键链路 E2E、构建预算、测试环境逐域验收和不可变目录回滚。

## Migration Plan

1. 建立基线：冻结现有 59 项渲染测试、补充当前关键链路 E2E、记录各路由资源清单和 API 调用次数。
2. 建立共享基础：实现 Session/Consent 守卫、安全 next、路由常量、错误边界、页面外壳与导航测试，不改变业务入口。
3. 提取业务模块：先移动纯展示组件和域级 CSS，再提取 home/my 只读数据 hooks；保持旧入口可运行。
4. 迁移公开与只读域：上线 `/`、`/login`、`/consent`、`/home`、`/my` 及只读详情，验证直接访问、刷新和返回。
5. 迁移建档域：用具名 reducer 替换 profile 数字 step，增加版本化 sessionStorage 草稿与 preview/confirm 幂等恢复。
6. 迁移每日指引域：建立 `/daily` 状态机和 `/daily/report?date=...`，覆盖生成任务离开/恢复、失败重试和种子结算不重复。
7. 清理兼容层：删除已迁移 `profileSteps` 分支、不可达 R1.1 原型引用和全局业务样式；确认根路由不依赖旧单体。
8. 发布：按项目规则逐阶段提交并推送；部署前拉取/核对测试服务器当前版本，构建静态导出到新不可变目录，验证所有固定路由直接访问、API/Worker、Nginx、gzip 和性能预算后切换。
9. 回滚：任一阶段可将 `frontend/current` 原子指回上一不可变发布目录并 reload Nginx；本变更无数据库迁移和后端契约变更，不执行数据降级。若新 URL 已被用户访问，旧版本 Nginx 临时将这些固定路径回退到 `/`，避免返回 404。

## Open Questions

- 是否在后续独立变更中将固定资源路由升级为 Next.js 动态段，取决于是否从静态导出迁移到常驻 Next.js 服务；不阻塞本次实施。
- 是否引入 TanStack Query 等请求缓存库由基础迁移阶段的重复请求与失效复杂度数据决定；默认不新增依赖。
