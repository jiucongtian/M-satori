## Why

R1.0 H5 目前将约 166 个逻辑页面集中在单个 `app/page.tsx` 中，以 React `view/step` 内存状态模拟导航，导致首包解析成本、浏览器返回与刷新恢复、深链接、监控定位和多人维护能力都受到限制。现阶段核心链路与真实 API 已稳定，适合在不改变业务语义、不影响现有用户路径的前提下，迁移到“业务域路由 + 域内状态机”的可持续架构。

## What Changes

- 为公开入口、今日首页、建档、每日指引、我的及其核心详情建立稳定的真实 URL；欢迎、登录和协议守卫保持清晰边界。
- 将连续、短生命周期的建档/生成流程保留为域内状态机，避免把弹窗、加载态、确认态和每个表单步骤过度路由化。
- 按业务域拆分组件、样式和客户端 chunk，确保访问首页时不加载未进入业务域的实现代码。
- 建立统一的认证恢复、协议更新守卫、默认回退路径和浏览器历史规则，支持刷新、直接打开链接、前进/后退及无历史记录场景。
- 为每日报告、档案详情和生成任务定义可恢复的资源标识；临时表单状态采用受控持久化，并明确敏感出生资料不得进入 URL。
- 保持现有 `/api/v1` 契约、会话 Cookie、幂等和账务语义不变；迁移期间保留旧入口兼容和可独立回滚能力。
- 采用分阶段、可验证的迁移顺序，每一阶段增加路由、状态恢复、权限、性能和核心业务回归测试，防止功能退化。

## Capabilities

### New Capabilities

- `h5-domain-routing`: 定义 R1.0 H5 的业务域路由、域内状态机、认证与协议守卫、刷新/返回/深链接恢复、按域加载及迁移兼容要求。

### Modified Capabilities

无。当前 `openspec/specs/` 不存在需要修改的既有能力规范；本变更不调整后端业务契约。

## Impact

- 主要影响 `frontend/app/`、`frontend/src/components/`、新增的业务域模块、全局与域级样式、前端渲染/导航测试及构建产物检查。
- Next.js App Router 将从单一 `/` 页面扩展为多个业务域路由，但仍使用客户端导航，不引入传统多页整页刷新。
- 登录恢复、协议确认、首页概览、每日指引、档案与种子接口调用方式需要重新组织，但 `/api/v1` 路径和 OpenAPI 不变。
- Nginx 继续使用静态导出与 SPA/静态文件服务能力；部署流程需要验证所有新增静态路由可直接访问且不会错误回退。
- 需要保留测试环境现有前端发布目录作为回滚点，并以首包体积、刷新恢复、浏览器历史和核心登录/建档/每日指引链路作为发布门槛。
