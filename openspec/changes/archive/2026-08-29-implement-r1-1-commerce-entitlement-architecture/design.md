## Context

R1.0 后端已经采用 NestJS/TypeScript 模块化单体，API 与 Worker 分离部署，PostgreSQL 保存业务事实，并具备 Drizzle 事务、数据库幂等记录、Outbox、BullMQ、GenerationTask 和只追加智慧种子流水。R1.1 将在此基础上新增真实商品、人民币支付、三档月会员、专项权益包、智慧种子活动价、固定核销和普通订单退款。

现有 `SeedLedgerService` 以用户级 `available/reserved` 总余额工作，`DailyInsightService` 直接调用具体账本。该模型能够保证基础并发结算，但不能表达种子批次、适用服务、独立有效期，也不能承载人民币购买权益和会员权益。R1.1 必须在不把种子变成统一钱包的前提下，为今日能量、抽卡问事和未来服务提供可复用的消费协议。

业务已确认：采用模块化单体；服务权益账本与智慧种子账本分离；抽卡前预留且 30 分钟未抽卡自动释放；核销来源完全由系统固定规则决定；权益包可重复购买并独立按自然日到期；会员升级全额购买新方案，旧周期剩余权益不退款、不抵扣、不结转，仅做内部剩余价值测算。

## Goals / Non-Goals

**Goals:**

- 建立商品、报价、订单、支付、交付、会员、权益和核销的清晰领域边界，禁止跨模块直接改表。
- 保证资金、权益、种子和业务交付各有独立状态机，并通过稳定业务 ID 全链路关联。
- 支持弱网、重复点击、重复支付回调、Worker 重放和多端并发下的幂等处理。
- 复用现有 PostgreSQL 事务、Outbox、Worker 和 GenerationTask，避免为 R1.1 引入分布式事务。
- 让今日能量、抽卡问事及未来服务只依赖中立消费端口，不感知具体账本结构。
- 保证所有商品版本、报价、订单、权益来源、核销决策、人工调整和资金反向操作可审计。

**Non-Goals:**

- 不拆微服务，不引入 Kafka、服务网格、事件溯源平台或 Kubernetes 强依赖。
- 不建设智慧种子充值、提现、转账、固定人民币汇率或跨服务通用钱包。
- 不开放自动续费、季度会员、年度会员、即时降级或多个并行有效会员周期。
- 不允许用户选择核销来源或保存核销偏好。
- 不在本变更实现完整抽卡问事内容生成；本变更提供其购买、预留、核销和恢复基础。
- 不把会员升级旧周期剩余价值接入退款、抵扣或财务应付流程。

## Decisions

### 1. 采用模块化单体和严格模块所有权

新增模块划分为 `catalog`、`pricing`、`order`、`payment`、`fulfillment`、`membership`、`entitlement`、`complimentary-seed` 和 `consumption`。各模块拥有自己的表、领域对象、应用服务与公开端口；Controller 不直接访问 ORM，模块不得直接更新其他模块拥有的表。

同步命令通过 TypeScript 应用端口调用，跨状态机的长事务通过领域事件、Outbox 和幂等消费者推进。相比立即拆微服务，该方案保留本地事务和简单部署；相比继续堆叠全局 Service，它可以通过依赖边界测试保持未来拆分能力。

### 2. 商品身份、商品版本、活动规则和报价分离

`ServiceOffering` 是稳定商品身份，`OfferingVersion` 是发布后不可变的价格、权益规格、有效期、购买限制、协议和退款规则版本。`SeedPromotionRule` 独立定义种子门槛与活动人民币价，不建立种子人民币汇率。

`CheckoutQuote` 针对用户、商品版本和当时资格生成，有效期 15 分钟。H5 只能提交 `offeringId`、`offeringVersion` 和 `quoteId`；服务端重验资格后创建订单。订单保存报价与商品完整快照，商品后续改价不影响历史订单。

### 3. 订单、支付、交付和退款分别维护状态

`MoneyOrder` 记录用户购买请求与快照；`PaymentAttempt` 记录一次支付渠道尝试；`FulfillmentJob` 记录支付后发放权益或会员的过程；`Refund` 只处理普通订单和异常资金反向操作。

本阶段 `PaymentProvider` 使用服务端确定性 Fake 自动成功来跑通完整业务闭环，并保留隔离的微信 API v3 适配器公共能力。Fake 成功只来自服务端 Provider 结果；启用真实微信后，成功只能来自验签回调或主动查单，两种模式都不能以来自前端成功页的状态作为资金事实。支付成功后通过 Outbox 创建交付任务；交付失败自动重试，最终无法履约时普通订单进入异常原路退回。

订单状态、支付状态、交付状态和退款状态不得合并成单一枚举。报价过期后不能下单；未支付订单创建 30 分钟后关闭。

### 4. 服务权益与智慧种子采用两套独立账本

人民币购买权益与会员权益写入 `EntitlementGrant` 批次及 `EntitlementUsageEntry` 只追加流水。每个批次保存服务类型、来源、总量、可用量、预留量、生效时间、到期时间和规则版本；购买多个权益包产生多个独立批次。

智慧种子写入 `ComplimentarySeedGrant` 批次及 `ComplimentarySeedEntry`，独立保存来源、适用服务范围、有效期、活动规则和余额投影。现有用户级种子账户保留为查询投影，不再作为唯一结算事实。

两套账本分别实现 `BenefitSourcePort` 的候选查询、预留、提交和释放能力，但不共享表、不合并余额，也不允许跨账本原子修改。

### 5. 核销编排统一协议，来源选择固定

具体业务提交 `ServiceRequirement`，至少包含 `userId`、`businessSpace`、`serviceType`、`quantity`、`businessContextType` 和 `businessContextId`。`consumption` 模块创建 `EntitlementResolution`，从两套账本取得候选并按固定规则选择：

1. 当前周期内适用且即将失效的会员权益；
2. 最早到期的专项购买权益包；
3. 最早到期的适用智慧种子批次；
4. 无可用来源时返回购买建议。

用户不能更改选择。决策记录保存候选快照、选中来源、推荐原因和规则版本。付费或会员问事按一次完整问事核销 `1 READING_CREDIT`；种子成本由卡数和规则版本计算。

### 6. 消费意图负责预留、核销和恢复

核销决策成功后创建 `ConsumptionIntent` 并调用选中账本预留。抽卡业务必须在预留成功后才能冻结服务端随机卡牌。

未正式抽卡的预留 30 分钟后过期并由定时扫描任务释放；抽卡后业务将消费意图标记为 `RUNNING`，取消 30 分钟超时并交给 GenerationTask 终态管理。完整报告通过质量校验后提交核销，失败或取消时释放。所有命令以 `consumptionIntentId + action` 建立唯一业务键。

跨模块崩溃恢复依赖可查询的消费意图和账本流水，而不是长数据库事务。例如账本已预留但业务尚未记录成功时，业务可以按 `businessContextId` 查询并重放，不重复占用权益。

### 7. 权益包按购买批次和自然日独立到期

权益包支付成功后，以 `Asia/Shanghai` 的支付成功日期作为第 1 个自然日，在第 N 个自然日 `23:59:59.999` 到期，数据库存储对应 UTC 时间并保存 `expiryTimezone` 与规则版本。同类权益包允许重复购买，不延长或合并既有批次；固定核销规则按 `expiresAt ASC, grantedAt ASC, id ASC` 选择。

### 8. 会员身份和具体权益分离

`MembershipSubscription` 管理方案、30 天周期、状态、来源订单和发放权益引用，不直接充当余额。当前周期未到期时手动续费创建排队周期，接在当前周期之后；到期后购买立即开始。下一周期权益仅在周期开始时发放，未使用权益不结转。

用户同一业务空间最多存在一个 ACTIVE 周期和一个有序的未来周期队列。周期开始、到期和权益发放通过幂等任务执行。

### 9. 会员升级使用替换式 Saga，不进入旧订单退款

`MembershipUpgrade` 关联旧订阅、新订单和新订阅。新订单按新方案全额支付；交付成功后新 30 天周期立即开始并发放新权益，旧周期同时终止，旧权益批次追加作废流水。

系统计算旧周期 `remainingTimeRatio`、`remainingQuotaRatio` 和 `residualValueEstimate`，保存 `assessmentRuleVersion`，仅用于内部分析、客服审计和产品策略。该数值不抵扣新订单、不产生 `Refund`、不调用支付退款、不进入财务应付，也不展示退款说明。升级确认页必须说明原方案结束且剩余次数不保留。

如果新订单支付成功但新方案最终无法履约，处理的是新订单异常原路退回，与旧周期剩余价值无关。

### 10. 幂等、并发和事件可靠性

所有命令要求 `Idempotency-Key`，数据库业务唯一约束作为最终防线。账本批次更新使用行锁或带版本条件的原子更新；同一预留只能提交或释放一次。支付渠道事件以 `provider + providerEventId` 去重，一个订单只能存在一个成功资金事实。

跨模块事件写入与领域状态在同一 PostgreSQL 事务中提交到 Outbox。消费者维护 Inbox/消费记录或等价唯一业务键，允许至少一次投递。定时对账覆盖未发布 Outbox、支付成功未交付、超时订单、悬挂预留、会员周期未发权益和账本投影不一致。

### 11. 隐私、审计和人工操作边界

商业模块只保存 `businessContextType/businessContextId`，不得读取问事问题或报告正文。支付回调原文按最小必要范围加密或脱敏保存，密钥与证书从环境注入。

人工补发、恢复、作废和冲正必须通过受控应用命令追加流水，记录操作者、原因码、备注、关联订单/任务和请求 ID。后台不得直接修改账户或批次余额。

### 12. API 契约与模块依赖方向

H5 API 按商品/报价、订单/支付、会员、权益/流水、普通退款和消费确认分组。核销来源切换接口不实现；消费响应只展示系统选中的来源、成本、到期时间和使用后余额。

依赖方向为业务模块 → `ConsumptionPort`，`consumption` → 两类 `BenefitSourcePort`；`payment` 不依赖会员或权益；`fulfillment` 通过命令端口调用会员或权益；`membership` 通过权益发放端口创建批次。模块边界测试禁止反向引用和跨模块 ORM 表导入。

## Risks / Trade-offs

- [模块化单体仍共享数据库，开发者可能跨模块查询或改表] → 为每张表声明所有者，限制 repository 导出，并增加依赖和表访问边界测试。
- [两套账本增加实现量] → 共享端口和测试契约，不共享领域表或现金语义；优先交付 count 类型，再扩展分钟和报告单位。
- [事件最终一致导致支付后短暂显示“发放中”] → 明确 `PAID/FULFILLING` 状态、自动重试、用户可查询状态和交付对账告警。
- [固定核销可能消耗用户原本想保留的来源] → 使用明确且版本化的固定优先级，核销前后展示实际来源，并保留完整决策快照供客服解释。
- [自然日到期在时区和夏令时环境容易歧义] → R1.1 固定 `Asia/Shanghai` 计算并保存 UTC 结果与时区；未来国际化通过规则版本扩展。
- [会员升级会作废旧权益且不退剩余价值] → 支付确认前明确提示旧方案结束和剩余次数不保留；内部保留测算与操作证据，不将其包装成退款。
- [现有种子总余额迁移到批次可能出现历史来源不完整] → 创建带迁移来源和版本的 opening grant，对账迁移前后 available/reserved，总历史只读保留。
- [支付渠道重复、乱序或伪造回调] → 强制验签、金额/商户/订单复核、provider event 去重、主动查单和独立资金对账。

## Migration Plan

1. 冻结本变更六份 capability spec、状态机、枚举、错误码、事件和 OpenAPI 候选契约。
2. 以 expand-only 迁移创建商品、报价、订单、支付、交付、会员、权益批次、种子批次、核销决策、消费意图和对账表，不修改现有 R1.0 表语义。
3. 实现模块端口、边界测试、Fake PaymentProvider 和确定性时钟，先打通无真实支付的商品报价与已有权益核销。
4. 将现有种子余额迁移为 opening grant，校验迁移前后余额与 reserved；旧表保持只读回退能力。
5. 让 `daily-insight` 通过 `ConsumptionPort` 双写/影子校验，确认一致后停止直接调用 `SeedLedgerService`。
6. 打通已有权益 → 预留 → 交付 → 核销/恢复，再接入 card-reading，不先接支付。
7. 接入订单、确定性 Fake 支付和交付 Saga，先完成无真实资金的全流程灰度；支付成功未交付保持可重试和可对账。
8. 依次开放权益包、会员开通/续费、普通退款，最后开放会员升级。
9. 执行并发、重复回调、Worker 崩溃、悬挂预留、跨日到期、迁移对账、升级和异常原路退回 E2E。

回滚时先关闭商品和支付 Feature Flag，停止创建新订单及新消费意图，保留 Worker 完成或补偿已支付订单。数据库采用 expand/contract，不删除资金、权益或流水事实；账务错误只能通过反向流水修复。种子迁移阶段可切回旧读取投影，但已经通过新账本产生的事实不得逆向覆盖。

## Open Questions

- 各普通商品的退款资格、可退比例和使用后规则需要在上线前以版本化 `RefundPolicy` 配置冻结，但不影响模块边界。
- 真实微信支付明确后置到独立变更：届时需确认 JSAPI、H5 或双通道，并补充 OpenID/OAuth 或可信客户端 IP、安全返回地址等场景能力。
- 真实微信支付变更启用前，支付与运维负责人需通过 Secret 提供商户号、证书、回调域名，并冻结主动查单频率和财务对账文件获取方式；当前 R1.1 不收集这些凭据。
- 智慧种子按 1 至 5 张卡的具体消耗数量、活动价门槛和恢复规则需要进入版本化配置。
- 商品正式价格、购买上限、权益包有效天数和会员权益数量以运营发布版本为准，不写入代码常量。
