# Satori Release SOP

> 适用范围：Satori 前端、后端、H5 原型、接口契约、数据库迁移和测试环境发布。
>
> 核心原则：GitHub Issues 是问题唯一事实源；代码、测试、部署、验收均通过 Release 批次建立关联，不另建重复问题台账。

## 1. 触发方式与批次模型

以下任一情况触发 Release SOP：

- 一个功能或缺陷完成，准备提交验证；
- 多个 Issue 完成，准备合并提交和统一回归；
- 原型、接口契约或数据库变化需要同步发布；
- 测试环境或正式环境需要部署新版本。

允许多个 Issue 组成一个发布批次。批次编号格式：

```text
R1.0-REL-001
R1.1-REL-001
```

候选发布版本格式：`r1.0.3-rc.1`；正式标签格式：`r1.0.3`。

每个批次只维护一份 `docs/releases/<批次编号>.md`，由
`docs/templates/发布批次记录.md` 创建。具体问题始终留在 GitHub Issues。

## 2. 固定状态面板

每次执行和汇报统一使用以下状态：

- `未开始`
- `进行中`
- `已完成`
- `待验证`
- `已阻塞`
- `不适用`

固定展示 12 个板块：

| # | 板块 | 退出条件 |
|---|---|---|
| 1 | 发布范围与 Issue | Release、批次、范围、Issue、非本次范围已冻结 |
| 2 | 影响分析 | 前端、后端、数据库、原型、文档、分支影响均有结论 |
| 3 | 原型与产品文档 | 已更新并记录版本，或明确“不适用”及原因 |
| 4 | 前后端契约与协作文档 | OpenAPI、支持矩阵和交接文档已同步，或明确不受影响 |
| 5 | 代码与分支 | 代码完成，Commit、分支、目标分支和跨 Release 同步策略明确 |
| 6 | 自动化测试 | 新增/修改测试已入库，测试和覆盖率报告绑定 Commit |
| 7 | 自检与质量门禁 | 构建、类型、Lint、Diff、敏感信息和核心操作闭环检查通过 |
| 8 | 发布产物 | 前后端不可变产物、镜像/文件校验值、迁移版本已记录 |
| 9 | 测试环境部署 | 部署成功，健康检查通过，部署前版本和回滚点明确 |
| 10 | 测试环境验证 | Smoke、API、E2E、回归完成，统计与失败分析已记录 |
| 11 | 验收与 Issue 回写 | Issue 已更新为待验证/关闭，未通过项已回流 |
| 12 | 标签与发布归档 | Git Tag、GitHub Release、Release Notes 和遗留项已归档 |

## 3. 标准执行流程

### Gate 0：建立发布批次

1. 创建批次记录，填写 Release、批次编号、负责人和目标环境。
2. 冻结关联 Issue、页面编号、接口和明确不在本次范围的内容。
3. 记录前端、后端、原型当前基线 Commit。
4. 检查工作树，保护不属于本批次的本地修改。

**门禁：** 范围不清、Release 不明或存在未确认 P0 产品决策时，不进入开发完成阶段。

### Gate 1：Issue 与影响分析

1. 用户可见缺陷、功能、接口、数据、部署或安全变化必须关联 Issue。
2. 小型文案/格式修改可以关联批次，不强制单独建 Issue。
3. 分析是否影响：
   - H5 原型与页面 Release 标签；
   - 前端、后端和 OpenAPI；
   - 数据库结构、迁移和既有数据；
   - `release/r1.0`、`release/r1.1` 等并行维护分支；
   - `docs/研发协作与工作交接.md` 和支持矩阵。
4. 同一修复涉及多个 Release 时，记录 merge/cherry-pick 顺序，禁止手工复制代码形成分叉。

**门禁：** 每个影响域必须是“受影响 + 动作”或“不受影响 + 原因”，不得留空。

### Gate 2：代码、原型、契约与测试入库

1. 完成功能代码和对应自动化测试。
2. 产品表现或交互变化时先同步 H5 原型，保持原页面编号，不创建重复副本。
3. 接口字段、状态、错误码变化时更新 OpenAPI、生成类型和前后端协作文档。
4. 数据库变化必须提供向前迁移、兼容性说明和回滚约束。
5. Commit 信息关联 Issue 和批次；测试代码与功能代码进入同一分支。

**门禁：** 代码已修改但测试、原型或契约仍应改未改时，不允许构建发布产物。

### Gate 3：本地自检与质量门禁

按受影响范围执行：

- 前端：Lint、构建、单元/组件测试、核心 E2E、导航与返回路径测试；
- 后端：格式、Lint、类型检查、单元、集成、契约、E2E、覆盖率；
- 全局：`git diff --check`、敏感信息扫描、Mock/调试代码检查；
- 数据：迁移检查、账本/权限/幂等校验；
- UI：页面编号、Release 标签、原型还原和主要视口检查。

基础发布门槛：

- 构建成功率 100%；
- 核心业务闭环 100% 通过；
- P0 为 0；P1 阻断项为 0；
- Smoke 100% 通过；
- 自动化用例通过率不低于 98%；
- 新增核心业务代码覆盖率目标不低于 80%；
- 导航和返回路径 100% 通过。

覆盖率不足但不影响既定基线时，必须写明现状、原因和补齐计划，不能只写“测试通过”。

### Gate 4：版本、构建与部署准备

1. 记录本地/远程分支、Commit、Tag 和相对目标分支的差异。
2. 确认 GitHub 已同步且 CI 通过。
3. 构建不可变前端产物和后端镜像，记录校验值。
4. 明确部署前版本、数据库迁移版本、备份需求和回滚步骤。
5. 测试服务器任何数据删除、覆盖或清理操作，必须事先取得产品负责人明确确认。

**门禁：** 无回滚点、产物不可追踪、CI 失败或存在未授权破坏性数据操作时，禁止部署。

### Gate 5：测试环境发布与自动化验证

1. 使用已固化部署方式发布测试环境。
2. 验证服务、反向代理、静态资源、API 和数据库迁移健康状态。
3. 执行 Smoke、API、E2E、核心业务闭环、旧功能回归和控制台错误检查。
4. 测试报告至少展示：
   - 总用例、通过、失败、跳过；
   - 通过率；
   - 单元测试覆盖率（行/分支/函数/语句）；
   - 核心闭环通过率；
   - P0/P1 数量；
   - 本次新发现问题及失败原因。
5. 失败项创建/关联 Issue，写明是否阻断、责任域、处理状态和复测结论。

**门禁：** 阻断门槛未满足时结论必须是“不允许发布”，不得以“基本通过”替代。

### Gate 6：验收、标签与归档

1. 自动化验证通过后，将相关 Issue 更新为 `status:needs-verify`。
2. 产品验收通过后关闭 Issue；未通过则重新进入修复批次。
3. 正式发布使用与测试环境验证完全相同的不可变产物。
4. 创建 Git Tag 和 GitHub Release，附功能、修复、限制和回滚信息。
5. 完成批次记录和 Release 测试汇总，遗留项归属到明确的后续 Release。

## 4. 批量问题发布规则

一次修改多个问题时：

1. 每个问题仍保留独立 Issue，批次记录只引用，不复制问题正文。
2. 为所有 Issue 增加相同 `batch:<批次编号>` 标签。
3. 测试分为“每个 Issue 的定向用例”和“整个 Release 的回归用例”。
4. 任一 P0 或阻断型 P1 失败，整个批次不得发布；可从批次移除该 Issue 后重新冻结范围。
5. 一个批次允许多次候选版本：`rc.1`、`rc.2`，每次均保留对应 Commit、产物和测试结果。
6. 修复进入多个 Release 时，先修最低仍维护版本，再按依赖顺序向后合并并分别回归。

## 5. 自动执行边界

默认由 Codex 连续完成：影响分析、代码、测试、文档、Git 状态核验、构建、测试环境部署、自动化验证、Issue 回写和结果汇总。

以下情况暂停并请求确认：

- Release 范围或产品预期存在实质歧义；
- 正式环境发布；
- 数据删除、覆盖、不可逆迁移或大范围数据修正；
- 需要新增外部权限、密钥或付费资源；
- P0/P1 的风险接受或测试门槛豁免。
