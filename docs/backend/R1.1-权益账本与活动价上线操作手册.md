# R1.1 权益账本与活动价上线操作手册

## 目标与边界

本版只使用统一消费流程和智慧种子批次账本。`SEED_BATCH_READ_MODE`、`DAILY_INSIGHT_CONSUMPTION_MODE` 已删除，不能通过配置切回旧扣费。

每日指引的新建、成功核销、失败释放、重试均使用消费意图。注册和赠礼只写新账。商城活动价仍在下单时预留指定种子、支付成功时核销、订单关闭时释放；与服务权益消费共用新版种子账本。

旧 `seed_accounts`、`seed_entries` 暂不删除，仅供迁移和历史查询。注册奖励记录、每日指引历史结算字段仍引用旧流水。保留表不代表继续双写。

## 部署前准备

1. 按发布 SOP 先拉取服务器最新代码，完成冲突合并；确认待部署版本包含服务器变更，再构建同一版本的 API 和 Worker。
2. 记录当前提交、镜像、环境文件和数据库迁移版本。将数据库完整备份及旧种子表单独备份保存到受限备份目录，校验文件，并在隔离库验证完整备份可恢复。测试数据不得进入正式环境。
3. 停止新的注册/赠礼、每日指引、活动价订单及后台种子发放/调整入口，防止迁移中继续写账。先让旧版本 Worker 结清已有任务和支付订单；支付回调、查单和补偿仍需排空。确认无在途处理后暂停所有 API/Worker/维护任务写入，迁移和核验期间保持停写。
4. 备份必须覆盖最后一次旧账写入之后的状态。服务器使用 Docker 时，通过对应数据库容器执行相同备份操作。以下示例在已配置 `PGSERVICE` 或受限 `PGPASSFILE` 的数据库客户端执行，`SEED_BACKUP_DIR` 指向本次发布独立目录：

```sh
mkdir -p "$SEED_BACKUP_DIR"
chmod 700 "$SEED_BACKUP_DIR"
pg_dump -Fc -f "$SEED_BACKUP_DIR/database.dump"
pg_dump -Fc -t public.seed_accounts -t public.seed_entries -f "$SEED_BACKUP_DIR/legacy-seeds.dump"
shasum -a 256 "$SEED_BACKUP_DIR/database.dump" "$SEED_BACKUP_DIR/legacy-seeds.dump" > "$SEED_BACKUP_DIR/SHA256SUMS"
pg_restore --list "$SEED_BACKUP_DIR/database.dump"
```

单独表备份依赖用户、枚举等原数据库结构，不能替代完整备份。不要在命令输出或交付证据中记录密码。

## 停写窗口内迁移与发布

使用待发布版本的运维命令，但暂不启动新版 API/Worker。先执行新增结构迁移，再做数据迁移：

```sh
npm run db:migrate
npm run db:preflight-seed-batches
npm run db:migrate-seed-batches
npm run db:preflight-seed-batches -- --require-migrated
npm run db:reconcile-seeds
```

所有命令必须成功，保存完整报告。迁移脚本执行前自动预检，执行后自动运行严格核验。

阻断条件包括：

- 旧账户仍有冻结余额。
- 旧每日指引仍在等待/生成中，或失败任务没有完成释放/退款。应由旧版本结清后再迁移，不能把冻结余额简单当可用余额复制。
- 新批次余额与新账户汇总不一致。
- 没有迁移批次、已有新批次且新旧余额或累计值不一致。这类混合状态无法仅凭“已有新批次”证明迁移完成；逐笔核查两边流水、恢复/补齐差异后再重跑，不得整额重复追加。
- 严格核验发现旧账户缺少新账户，或空批次账户的余额/累计值尚未迁入。

迁移幂等：已迁移账户重跑不得覆盖后续新账消费。零可用余额账户也保留累计收入/消费。已领取注册奖励在重放领取接口时不再新增赠送。

验证通过后，清除两个废弃环境变量，启动同一版本 API 和 Worker，恢复入口。历史失败且已结清的每日指引再次重试时，创建新的统一消费意图；不再使用旧账扣费。

## 验收

- 抽查零余额、有余额、老注册奖励、历史消费、会员和服务包用户，迁移前后可用余额一致。
- 注册赠礼并发领取、重复领取只发一次；已经消费后重复领取不会恢复旧余额。
- 每日指引新建预留、成功核销、失败释放、失败重试和重复回调不会多扣。
- 活动价订单取消/超时释放、支付成功只核销一次；标准价订单不扣种子。
- 余额和累计统计来自新账；历史流水仍可查询，迁移批次不显示成新赠送。
- 观察旧表没有新增或更新记录；新批次账本对账无差异。

## 观察、回滚与旧表删除

切换后观察至少 24 小时，覆盖支付恢复、失败重试、种子过期和注册赠礼；按业务量延长观察期。

未开放写入前，可使用已验证的完整备份恢复旧版本。开放新版写入后，不能仅回滚代码或恢复旧余额：先停写，保存新备份，核对并保全切换后的订单、支付和消费事实，制定差异恢复方案。

确认稳定后另行执行旧表删除变更：先将需在线保留的旧流水归档或迁入历史查询存储，移除历史查询 SQL 和注册奖励/每日指引外键依赖，再备份、验证恢复、删除旧表。不得使用 `DROP ... CASCADE` 绕过这些依赖。本次代码变更不包含删表操作，也不删除整个业务数据库。
