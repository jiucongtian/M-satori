# R1.1 智慧种子单账本切换与旧账本删除上线操作手册

## 何时需要执行本手册

本手册是一次性的迁移边界操作，不是每次发布都要执行。只有“当前生产数据库尚未应用 `0022`，目标版本首次包含 `0022_cooing_prodigy.sql`”时，才执行下文的停写、旧表专项备份、三端协调切换和跨迁移回滚方案。

| 当前生产数据库 | 目标版本 | 处理方式 |
| --- | --- | --- |
| 尚未应用 `0022` | 不包含 `0022` | 不执行本手册；按目标版本原有发布流程处理。 |
| 尚未应用 `0022` | 包含 `0022` | 正在跨越删表边界，必须完整执行本手册。 |
| 已应用 `0022` | 包含 `0022` 或更高版本 | 已跨过边界，按常规生产发布流程；不要再次执行旧表备份或删表步骤。 |
| 已应用 `0022` | 目标版本早于 `0022` | 属于不兼容降级，禁止代码单独回退；按本手册“回滚与事故恢复”制定数据库恢复或向前修复方案。 |

发布准备阶段应先根据发布记录和只读 Schema 检查确定当前状态。`seed_accounts` 与 `seed_entries` 同时存在，表示尚未跨过边界；两表同时不存在，表示已经跨过边界。若只有一张表存在、旧关联字段状态不一致，或迁移记录与 Schema 相互矛盾，必须停止发布并人工诊断，不得猜测或重复执行迁移。

## 目标与不可逆边界

智慧种子余额、赠送批次、分配和用户可见流水统一使用以下新版表：

- `complimentary_seed_grants`
- `complimentary_seed_allocations`
- `complimentary_seed_entries`
- `complimentary_seed_account_projections`

迁移 `backend/drizzle/0022_cooing_prodigy.sql` 会永久删除旧 `seed_accounts`、`seed_entries`、`seed_entry_type`，并删除 `registration_rewards.seed_entry_id`、`daily_insights.seed_reservation_entry_id`、`daily_insights.seed_settlement_entry_id`。用户端不再展示旧版交易历史；需要审计时只能使用上线前受限备份，不得把旧流水重新接回在线查询。

这不是普通兼容性迁移。旧版用户 API 和旧版运营 API 都会查询 `seed_accounts`，旧表删除后会直接报错。因此首次跨越 `0022` 边界的生产发布必须把用户端前端、API、Worker、运营 Web、运营 API 和迁移/Seed 作为同一个协调发布批次，全部来自同一 `TARGET_SHA`。禁止只执行迁移、只更新主站或让运营后台停留在旧版本；数据库已经应用 `0022` 后，此项恢复为常规版本一致性要求。

测试环境已在 `release/r1.1@e3cde9df0be34f806529719ada8cf106a204e253` 完成一次完整演练：迁移前 78 个旧账户、148 条旧流水均已备份并在隔离库恢复；迁移后新版账本对账 79 个账户、0 个不一致。该结果只证明流程可行，不代替生产环境自己的数据核验、备份恢复演练和明确授权。

## 生产发布阻断项

仅在本次发布跨越 `0022` 边界时，以下任一项未满足都禁止开始生产写操作：

1. 生产目标、主机、域名、服务和当前版本尚未从正式基础设施清单确认，或仍借用测试环境路径、配置、短信模式。
2. `TARGET_SHA` 未推送到 GitHub，或 GitHub、待发布源码、用户端及运营端产物不是同一提交。
3. 生产仍有非零旧账户缺少 `complimentary_seed_account_projections`。
4. 存在 `PENDING` / `GENERATING` 且没有 `consumption_intent_id` 的每日指引。
5. 新版批次、分配、流水与账户投影对账不一致。
6. 注册赠送、每日指引、活动价订单、支付回调、补偿任务或运营人工赠送仍在写入，无法建立完整停写窗口。
7. 没有“停写后的最终完整备份”和旧表专项备份，或完整备份未在隔离数据库实际恢复成功。
8. 未记录旧用户端、旧运营后台、数据库迁移边界和恢复负责人，或仍计划通过单独切回旧代码完成回滚。
9. 未针对本次精确主机、Commit、组件范围、删表影响和恢复方案取得生产发布及不可逆数据操作的明确授权。

迁移自身还会再次检查第 3、4 项并在不满足时抛错；这只是最后保险，不能代替发布前预检。

## 发布前准备

1. 按 Release SOP 拉取并合并 GitHub 最新分支，完成发布前 freshness barrier，记录完整 `TARGET_SHA` 和短 `RELEASE_ID`。
2. 从 `TARGET_SHA` 构建用户端前端、后端镜像、运营 Web/API；记录产物校验值。不要从开发工作区或服务器脏工作区构建。
3. 盘点并记录生产当前用户前端、API/Worker、运营 Web/API、迁移版本、镜像、环境文件、Nginx 和回滚目录。
4. 将所有新产物先上传到不可变发布目录，复制服务器专用环境文件并保持 `0600`；此阶段不切流、不启动迁移。
5. 使用生产数据执行只读预检和新版账本对账。抽查零余额、有余额、老注册奖励、历史消费、会员、服务包和活动价订单用户。
6. 排空 Worker、支付回调、查单和补偿任务；暂停用户 API/Worker、运营 API 及所有维护任务的写入。运营 Web 可进入维护状态，但不能继续连接旧运营 API 执行写操作。
7. 停写后再次执行迁移前置查询，确认数据没有变化，再生成最终备份。

只读预检至少保存以下汇总结果，不输出用户级明细：

```sql
SELECT count(*) AS legacy_accounts FROM seed_accounts;
SELECT count(*) AS legacy_entries FROM seed_entries;
SELECT count(*) AS projected_accounts FROM complimentary_seed_account_projections;

SELECT count(*) AS unprojected_nonzero_legacy_accounts
FROM seed_accounts legacy
WHERE (
  legacy.available <> 0
  OR legacy.reserved <> 0
  OR legacy.total_earned <> 0
  OR legacy.total_spent <> 0
)
AND NOT EXISTS (
  SELECT 1
  FROM complimentary_seed_account_projections current_account
  WHERE current_account.owner_user_id = legacy.user_id
);

SELECT count(*) AS unsettled_legacy_daily_insights
FROM daily_insights
WHERE status IN ('PENDING', 'GENERATING')
  AND consumption_intent_id IS NULL;
```

后两项必须均为 `0`；否则保持旧版本运行并先修复数据，不能执行 `0022`。

## 停写后的备份与恢复演练

备份必须覆盖最后一次生产写入之后的状态。以下命令仅为数据库客户端示例；正式主机、容器、数据库服务和凭据来源必须从生产基础设施文档解析，不得照抄测试环境值。

```sh
mkdir -p "$SEED_BACKUP_DIR"
chmod 700 "$SEED_BACKUP_DIR"
pg_dump -Fc -f "$SEED_BACKUP_DIR/database.dump"
pg_dump -Fc -t public.seed_accounts -t public.seed_entries -f "$SEED_BACKUP_DIR/legacy-seeds.dump"
sha256sum "$SEED_BACKUP_DIR/database.dump" "$SEED_BACKUP_DIR/legacy-seeds.dump" > "$SEED_BACKUP_DIR/SHA256SUMS"
pg_restore --list "$SEED_BACKUP_DIR/database.dump"
```

随后必须在隔离数据库实际恢复 `database.dump`，至少核对迁移表、旧账户数、旧流水数、新账户投影数及关键业务表数量。单独的 `legacy-seeds.dump` 依赖用户、枚举和其他结构，只用于专项审计，不能替代完整备份。备份目录、校验值、权限和恢复结果写入发布记录，不记录密码、连接串或用户明细。

## 协调迁移与启动顺序

1. 确认用户和运营写入口均已暂停，重新记录当前运行版本和软链接作为代码回滚参考。
2. 在同一维护窗口内准备指向相同 `RELEASE_ID` 的用户端、后端和运营端发布目录；恢复流量前不允许出现不同版本组合。
3. 使用目标版本的迁移服务执行 `0022_cooing_prodigy.sql`。迁移必须以非 `CASCADE` 方式删除旧关联字段、旧表和旧枚举；任何保护检查或 SQL 失败都停止发布。
4. 执行法律文档 Seed 及 `npm run db:reconcile-seeds`，要求 `mismatchCount=0`。
5. 只读确认 `seed_accounts`、`seed_entries`、`seed_entry_type` 和三个旧关联字段均已移除，新账户投影与批次账本存在且可查询。
6. 启动同一 `TARGET_SHA` 的 API、Worker、运营 API 和运营 Web；全部健康后再恢复公网流量。
7. 校验 Nginx 后恢复用户端前端；确认 GitHub、服务器代码镜像、用户端前端、API/Worker、运营 Web/API 的版本和关键文件校验值一致。

不要再运行已经删除的 `db:preflight-seed-batches`、`db:migrate-seed-batches` 或 `seed-cutover-preflight.ts`。它们属于旧账迁入新版账本阶段，不是 `0022` 删表阶段的生产命令。

## 上线后验收

- API ready、Worker、PostgreSQL、Redis/队列、运营 API/Web 全部健康，迁移和 Seed 一次性任务以状态 0 退出。
- 首页、登录、Bootstrap、运营后台域名及其他生产必要入口返回预期状态。
- 新版账本全量对账 `mismatchCount=0`。
- 用户智慧种子余额和运营后台用户余额均来自 `complimentary_seed_account_projections`，两端抽样一致。
- 用户交易记录只展示 `complimentary_seed_entries` 中允许展示的新版业务流水，不再出现旧历史或迁移批次。
- 注册赠礼重复领取不重复入账；每日指引预留、核销、失败释放和重试正常；活动价订单取消/超时释放、支付成功核销保持幂等。
- 日志没有 `seed_accounts` / `seed_entries` 缺表错误，也没有新增持续性数据库或队列错误。

## 回滚与事故恢复

`0022` 之后不存在代码单独回滚路径：旧 API 或旧运营后台切回后会查询已经删除的表。旧发布目录和镜像只作为源码与产物参考，不能直接恢复流量。

- 如果迁移尚未执行，可协调恢复全部旧组件和原流量，不涉及数据库降级。
- 如果迁移已经提交、但新版尚未开放任何写入，停止全部服务后，可以使用已验证的完整备份恢复整个数据库，再协调恢复全部旧组件；不得只恢复两张旧表。
- 如果新版已经开放写入，禁止直接恢复上线前数据库，否则会丢失上线后的注册、订单、支付、权益和种子事实。必须先再次停写并保存故障时点完整备份，核对上线后增量，制定数据合并或向前修复方案，取得单独授权后执行。
- 迁移失败时不要自动降级数据库，不要使用 `DROP ... CASCADE`、全库覆盖或手工伪造余额绕过保护条件。

发布完成后至少观察 24 小时，覆盖注册赠礼、每日指引失败重试、活动价支付恢复、种子过期和运营人工赠送；按生产业务量延长观察期。
