# Satori R1.1 商业链路运维 Runbook

## 1. 适用范围与操作原则

本 Runbook 覆盖商品报价、人民币订单、微信支付、交付 Saga、服务权益账本、智慧种子账本、固定核销、会员周期、普通退款和自动对账。

- 所有排查先记录 `requestId`，再沿 `orderId`、`paymentAttemptId`、`fulfillmentId`、`subscriptionId`、`grantId`、`consumptionIntentId` 关联事实。
- 不直接更新余额、订单状态或会员状态；修复必须调用受 RBAC 保护的应用命令，并填写原因码、说明和关联业务 ID。
- 商业日志不得包含问事正文、报告正文、验证码、Token、微信支付参数、证书、私钥或 APIv3 密钥。
- 支付事实与交付事实分开判断。用户已支付但权益发放中时，禁止引导重复支付。
- 会员升级新方案未安全生效前保留原方案；升级旧周期的内部测算值不进入退款、支付或用户展示链路。

## 2. 支付故障

### 2.1 告警信号

- 支付失败数或回调验签失败数在短时窗口显著上升。
- 订单持续停留在 `PAYMENT_PROCESSING`，但支付渠道已有资金事实。
- 回调入口出现非可信代理来源、缺失微信签名头或异常大请求体。

### 2.2 排查与恢复

1. 用 `orderId` 查询订单、支付尝试和支付事件，核对商户号、金额、币种和 provider trade id。
2. 回调缺失时执行 PaymentProvider 主动查单；不得依据 H5 成功页人工改为支付成功。
3. 回调重复或乱序时确认 Inbox/支付事件唯一键已命中；不得删除去重事实后重放。
4. 确认资金成功后，检查同一订单是否存在多个成功资金事实；重复扣款只能走系统异常原路冲正，不撤销正常订单权益。
5. 回调验签异常时检查平台公钥轮换、服务器时间和原始请求体保存链路。禁止把回调原文输出到日志。
6. 支付渠道整体不可用时关闭新支付入口，保留查单和回调入口，使已发起订单继续收敛。

## 3. 悬挂预留

### 3.1 告警信号

- `consumption_intents` 长时间保持 `RESERVED` 且超过 `reservationDeadline`。
- ConsumptionIntent 状态与服务权益或智慧种子 reservation allocation 不一致。

### 3.2 排查与恢复

1. 以 `consumptionIntentId` 查询候选快照、选中来源、业务上下文 ID、预留流水和业务任务状态。
2. 尚未正式抽卡且超过 30 分钟时执行到期释放；释放命令使用固定业务键，允许安全重放。
3. 已进入 `RUNNING` 时不得按短超时释放；等待业务终态，成功执行 `COMMIT`，失败或取消执行 `RELEASE`。
4. 账本已预留但调用方未收到响应时，按 opaque `businessContext` 查询既有 ConsumptionIntent，禁止重新选择来源。
5. 自动修复仍不一致时创建 reconciliation case，由运营命令修复并保留审计记录。

## 4. 交付失败

### 4.1 告警信号

- FulfillmentJob 进入 `RETRY_WAIT`、超过预期延迟或达到最大尝试次数。
- 订单为 `PAID/FULFILLING`，但没有交付任务或来源权益引用。

### 4.2 排查与恢复

1. 以 `orderId` 核对支付成功事实、FulfillmentRequested Outbox、FulfillmentJob 和目标权益/会员资源。
2. Outbox 未发布时重投同一事件；Worker 崩溃时重放同一 `businessKey`，不得创建新交付键。
3. 权益已发放但任务未成功时，根据来源 ID 回读已有 grant 并完成任务，不得重复发放。
4. 会员已创建但任务未成功时，根据 `sourceOrderId` 回读 Subscription/Period 并完成任务。
5. 达到最终失败条件后进入异常补偿；普通订单由系统发起原路冲正，升级新方案失败则保留原会员。

## 5. 账本不一致与修复

### 5.1 服务权益账本

1. 比对 grant 投影的 `total/available/reserved` 与只追加 usage entries。
2. 比对有效 ConsumptionIntent 与 reservation allocations。
3. 缺少流水时使用受保护的 `ADJUSTMENT` 或重放原业务命令；不得直接修改 grant 投影。
4. 所有人工调整必须记录操作者、原因码、说明、requestId 和关联订单或业务 ID。

### 5.2 智慧种子账本

1. 比对批次 grant、allocation、entry 和兼容账户投影。
2. 迁移期同时查看新旧 available/reserved 影子报告；不一致时保持旧读模型回退开关。
3. 使用迁移/对账脚本生成差异报告；修复通过批次账本命令完成，不覆盖历史 seed entries。

## 6. 会员周期异常

1. 检查同一用户与业务空间是否只有一个 `ACTIVE` 周期。
2. 检查排队续费周期按 `startsAt/id` 有序，且未提前发放下一周期权益。
3. 周期已开始但权益缺失时，重放以 `periodId + serviceType` 为幂等键的发放命令。
4. 周期结束时确认未使用权益已通过 `EXPIRE` 只追加流水结束且没有结转。
5. 升级停在准备态时，先确认新方案权益完整，再终止旧周期并作废旧权益；任何一步失败都先保护原会员可用性。

## 7. 对账 case 生命周期与告警

- `OPEN`：自动检测到差异，尚未处理。
- `INVESTIGATING`：运营已接手并记录责任人与初步原因。
- `RESOLVED`：已通过应用命令修复，必须保存修复动作与证据。
- `IGNORED`：确认为无影响差异，必须记录批准人与理由。

`CRITICAL` case、支付成功未交付、账本不一致和周期漏发必须告警。告警恢复条件是事实重新对齐且 case 有可审计 resolution，不是简单关闭告警。

## 8. 发布与回滚检查

1. 发布前确认支付证书/密钥只通过 Secret 注入，回调入口仅由 Nginx 精确路径代理，API 端口仅绑定 localhost。
2. 执行 expand migration 后先验证旧 API、已有订单、旧权益/种子读取，再逐项开启新 Feature Flag。
3. 回滚 API/Worker 时不得回滚已使用的新数据库列或删除新表；旧版本必须能忽略新增结构。
4. 关闭新订单后继续运行回调、查单、Outbox、Worker、退款和对账，直到所有已支付订单完成或补偿。
