# Satori R1.0 配置参考

> 适用范围：API、Worker、迁移、Seed、测试环境和生产环境。
>
> 原则：环境变量只表达部署差异、外部依赖、密钥和容量；非敏感业务、安全与可靠性规则进入版本化策略；运行服务不提供 Mock/Stub 切换。

## 1. 配置来源与优先级

1. `backend/docker-compose.test.yml` 为测试环境强制注入 `HOST`、`PORT`、`DATABASE_URL`、`REDIS_URL`、`COOKIE_SECURE` 和 `SMS_DELIVERY_MODE=FIXED_CODE`，优先级高于 `.env.production`。
2. 其余部署变量由服务器专用 `.env.production` 注入，完整定义、允许值和影响见 `backend/.env.example`。
3. 产品、安全和可靠性规则来自 `backend/packages/infrastructure/src/config/runtime-policy.ts`，只能通过代码评审和发版修改。

应用启动时由 Zod Schema 校验部署变量。未知的历史变量不会改变运行策略，但发布时仍应从服务器文件移除，避免误导运维人员。

## 2. 保留的部署环境变量

| 类别          | 配置项                                                                                    | 影响范围                                |
| ------------- | ----------------------------------------------------------------------------------------- | --------------------------------------- |
| 进程与网络    | `HOST`、`PORT`                                                                            | 监听地址和端口映射                      |
| 数据基础设施  | `DATABASE_URL`、`DATABASE_POOL_MAX`、`REDIS_URL`                                          | PostgreSQL、Redis、API 和 Worker 可用性 |
| 队列容量      | `QUEUE_PREFIX`、`QUEUE_CONCURRENCY`、`QUEUE_JOB_TIMEOUT_MS`                               | 环境隔离、任务并发、超时与失联恢复      |
| HTTP 与安全   | `CORS_ORIGINS`、`COOKIE_SECURE`                                                           | H5 跨域和 Refresh Cookie 传输           |
| 应用密钥      | `CURSOR_SIGNING_SECRET`、`AUTH_HMAC_SECRET`、`ACCESS_TOKEN_SECRET`、`DATA_ENCRYPTION_KEY` | 游标、身份哈希、Token 和字段解密        |
| 短信供应商    | `SMS_DELIVERY_MODE`、`SMS_GATEWAY_URL`、`SMS_GATEWAY_API_KEY`、`SMS_GATEWAY_TIMEOUT_MS`   | 固定测试码或真实短信发送                |
| Aqua 基础连接 | `AQUA_BASE_URL`、`AQUA_SERVICE_KEY`                                                       | 同一 Aqua 租户及其全部 Workflow         |

`backend/.env.example` 对上表每个变量都使用固定格式说明：

```text
# 用途：为什么需要该变量
# 取值：允许值、格式或范围
# 影响：修改后会影响哪些服务或业务流程
KEY=value
```

配置单测会逐项核对 Schema 变量是否具有这三类注释；漏写说明会使测试失败。

四卡初识报告不是部署选项：所有环境固定使用本地确定性知识生成器，不存在启用开关、LOCAL/Aqua 选择器或环境专用超时配置。

完整每日指引与首页能量摘要属于同一 Aqua 租户，并由同一个 Service Key 调用租户下的不同 Workflow。两项连接配置由 `AquaClientFactory` 统一读取；业务模块不得再自行配置 Base URL 或 Service Key。Workflow、超时、重试和预热参数是代码策略，不是服务器差异。

## 3. 测试环境与生产环境切换指南

### 3.1 判断原则

从测试环境发布到生产环境时，应发布测试环境已经验收通过的同一代码提交和同一 `R1_RUNTIME_POLICY`。不得为了“适配生产”单独修改 Workflow、业务价格、认证时效、重试或预热规则。

只替换真正代表部署边界的值：基础设施地址、环境隔离前缀、对外域名和密钥。创建生产配置时复制配置项名称与结构，不复制测试环境的真实值。

### 3.2 各配置项是否需要变化

| 配置项                                   | 测试环境 → 生产环境 | 变更指导                                                                                                                                                       |
| ---------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HOST`、`PORT`                           | 通常不变            | 容器内建议继续使用 `0.0.0.0:3000`；公网端口由负载均衡、Ingress、Nginx 或容器端口映射控制。只有生产运行平台要求不同监听方式时才修改，并同步健康检查与上游配置。 |
| `DATABASE_URL`                           | 必须变化            | 指向独立的生产 PostgreSQL，使用生产专用账号和密码。禁止生产连接测试数据库；切换前先完成迁移、备份和恢复演练。                                                  |
| `DATABASE_POOL_MAX`                      | 可能变化            | 根据生产数据库连接上限、API/Worker 实例数和压测结果计算；没有容量证据时先沿用测试值，不能仅因为上线而盲目提高。                                                |
| `REDIS_URL`                              | 必须变化            | 指向独立的生产 Redis，启用认证和传输加密时使用对应安全 URL。禁止测试和生产共享队列、限流或锁数据。                                                             |
| `QUEUE_PREFIX`                           | 应当变化            | 即使 Redis 已物理隔离，也建议使用明确前缀，例如 `satori-test`、`satori-prod`；同一 Redis 内必须不同，避免跨环境消费任务和共享限流计数。                        |
| `QUEUE_CONCURRENCY`                      | 可能变化            | 根据生产 Worker 数量、数据库容量和 Aqua 限流验证后调整；初次上线优先沿用测试通过的值，再依据监控逐步增加。                                                     |
| `QUEUE_JOB_TIMEOUT_MS`                   | 通常不变            | 它定义任务失联与执行预算。只有生产真实耗时证明确有差异时才通过一次受测发布调整，不能作为临时扩容旋钮随意修改。                                                 |
| `CORS_ORIGINS`                           | 必须变化            | 改为生产 H5 的精确 HTTPS Origin；多个 Origin 使用逗号分隔。删除测试域名和本地开发域名，禁止使用 `*`。                                                          |
| `COOKIE_SECURE`                          | 保持 `true`         | 测试域名和生产域名都通过 HTTPS 时均为 `true`。本地纯 HTTP 开发才可使用 `false`；生产不得关闭。测试 Compose 已强制为 `true`。                                   |
| `CURSOR_SIGNING_SECRET`                  | 必须变化            | 为生产独立生成高强度随机值并通过 Secret Manager 注入。初始化后不要直接替换，否则已签发分页游标会失效。                                                         |
| `AUTH_HMAC_SECRET`                       | 必须变化            | 为生产独立生成，绝不能复用测试值。已有生产数据后不得直接替换，否则手机号、设备、验证码和 Session 派生值将无法匹配。                                            |
| `ACCESS_TOKEN_SECRET`                    | 必须变化            | 为生产独立生成。已有用户后直接轮换会使旧 Access Token 失效，必须按受控轮换方案执行。                                                                           |
| `DATA_ENCRYPTION_KEY`                    | 必须变化            | 为生产独立生成 32 字节密钥并保存备份。生产数据写入后不得直接替换，否则历史手机号等密文将无法解密；轮换必须先实现并验证双读/重加密方案。                        |
| `SMS_DELIVERY_MODE`                      | 必须变化            | 短信服务未接通前，测试环境使用 `FIXED_CODE`；生产上线前必须接通供应商并设置为 `GATEWAY`。生产禁止使用固定验证码。                                              |
| `SMS_GATEWAY_URL`、`SMS_GATEWAY_API_KEY` | 生产启用            | `GATEWAY` 模式下必须配置生产供应商地址和生产密钥。测试环境使用固定码时整行省略；做供应商联调时使用供应商测试账号，不复用生产密钥。                             |
| `SMS_GATEWAY_TIMEOUT_MS`                 | 通常不变            | 优先使用测试验证过的超时；只有供应商生产链路的延迟指标支持时才调整，并同步验证 API 资源占用和失败率。                                                          |
| `AQUA_BASE_URL`                          | 可能变化            | 如果 Aqua 测试与生产共用同一网关地址，可以保持不变；如果租户或环境使用不同入口，则改为生产 HTTPS 地址。完整每日指引与首页摘要在同一环境内始终共用这一个地址。  |
| `AQUA_SERVICE_KEY`                       | 应当变化            | 使用生产专用 Service Key，权限覆盖生产租户内所需 Workflow，不复用测试密钥。通过 Secret Manager 注入，不得写入 Git、日志或交接文档。                            |

`POSTGRES_PASSWORD` 是测试 Compose 创建自建 PostgreSQL 时使用的 Compose 级变量，不属于 Satori 应用 Schema。生产若也由 Compose 创建数据库，应使用独立生产密钥；若使用托管数据库，则以平台 Secret 和 `DATABASE_URL` 为准。

### 3.3 推荐切换步骤

1. 冻结并记录测试环境验收通过的代码提交、数据库迁移版本和 `configVersion`；生产发布使用完全相同的提交。
2. 从 `backend/.env.example` 建立生产 Secret 清单，只复制配置项名称，不复制测试值。
3. 创建独立的 PostgreSQL、Redis、应用密钥、短信凭据和 Aqua Service Key；设置生产 CORS Origin 与环境隔离前缀。
4. 对照上表逐项复核。重点确认生产未使用测试数据库、测试 Redis、固定验证码、测试域名或测试密钥。
5. 在不输出变量值的前提下检查必填项数量、重复项和历史变量；执行 Compose 配置校验、迁移、Seed，再启动 API/Worker。
6. 验证 ready、bootstrap 的 `configVersion`、登录短信、Cookie、首页缓存预热和完整每日指引；确认日志不包含密钥或敏感输入。
7. 保留上一生产发布目录和配套 Secret 版本。回滚代码时必须恢复与该代码版本匹配的配置，不能只切换代码目录。

生产环境的密钥首次设置后，应视为持久数据依赖，不得像普通参数一样直接覆盖。任何密钥轮换都应单独制定迁移、兼容、验证和回滚方案。

## 5. 首页摘要固定执行策略

首页 HTTP 请求只读共享缓存，不同步调用 Aqua。Worker 固定在启动时和每小时补齐今天及未来两天的六十甲子组合，采用并发 3、发车间隔 5 秒的受控负载。该逻辑是首页摘要成立的必要运行路径，不提供环境开关或服务器档位；调整时应修改版本化策略、补充测试并正常发版。

## 7. 发布检查

发布前执行：

```bash
npm run typecheck
npm run lint
npm run test:contract
npm run test:unit
npm run build
```

部署测试服务器前，先备份服务器 `.env.production`，将两个历史 Service Key 名称合并为 `AQUA_SERVICE_KEY`，删除上表已迁移的历史键，再执行 Compose。不得输出或复制任何密钥值。
