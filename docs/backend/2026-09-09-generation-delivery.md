# Redis 任务推送与商业队列隔离

## 行为变化

SSE 连接先验证任务归属，再注册共享 Redis 订阅，按数据库事件游标补读并推送。每个 API 进程最多使用一条独立的 Pub/Sub 连接，普通 Redis 命令连接不进入订阅模式。最后一条 SSE 断开时释放订阅连接。

Redis 通知是提示而非权威数据：初次订阅和重连都会触发补读；无通知时每 15 秒发送心跳并补查一次。旧 Worker 在数据库事务中发布通知，因此通知后额外安排一次 250 ms 延后补查；事务更慢或通知丢失仍由 15 秒兜底补齐。终态关闭前再次读取事件，避免漏掉读取间隙提交的终态事件。Last-Event-ID、现有事件名称和用户归属校验保持兼容。

生成相关任务仍使用 `<QUEUE_PREFIX>:generation`。所有 `commerce.*` Outbox 事件改投 `<QUEUE_PREFIX>:commerce`，由独立 CommerceTaskWorker 消费，涵盖履约、退款、重复支付退款和订单种子预留释放。`commerce.fulfillment.succeeded` 是完成事实，无额外执行动作；未知商业事件明确失败，避免静默丢弃。

两个消费者仍运行于同一 Worker 进程，分别使用 `QUEUE_CONCURRENCY` 和新增 `COMMERCE_QUEUE_CONCURRENCY`，默认各 5。隔离的是队列积压和并发槽位，CPU、数据库连接池和进程故障域尚未独立。账号注销任务继续留在 generation 队列，本次不改变其执行语义。

## 旧队列兼容及发布顺序

- 无数据库迁移，不清空、不重命名旧队列。
- 新版生成消费者领取旧队列的商业任务后，先转投 commerce 成功，再确认原任务完成；保留原 jobId、退避方式和剩余尝试预算。转投失败由旧任务自身重试，不提前确认。
- 旧积压里的商业任务仍需等待生成消费者领取才能转投；兼容转投不能承诺立即绕过已存在的 AI 积压。新 Outbox 投递直接进入独立队列。
- 发布时应保证新版 Worker 消费者上线后，再让新版 API 开始投递；同版 Worker 内也含 Outbox 发布器，短暂先投递后就绪不会丢任务，但应观测 commerce 积压。
- 滚动期间旧版发布器可能仍投到 generation，兼容转投会接住。重复投递沿用 Outbox ID；业务处理仍依赖既有幂等和账务事务，不能把队列去重当成 exactly-once 保证。
- 不能直接把所有消费者回退到不认识 commerce 的旧版本，否则已投递的新队列任务无人处理。需要保留新版商业消费者至任务清空（含 delayed/active/failed 的处置），或按单独评审的方案转投；不要删除队列作为回滚方式。

## 监测与验证

分别监测 generation/commerce 的 waiting、active、delayed、failed、最老任务年龄和完成速率；同时监测数据库连接等待、SSE 活跃连接、补查频率和 Redis 重连。增加商业并发前应按两个队列总占用评估连接池。

定向测试覆盖：空闲查询频率、通知合并、通知早于提交、漏通知补齐、Last-Event-ID、终态事件、归属校验、断开清理、共享订阅及重连、支付失败重试和旧任务转投预算。

真实 PostgreSQL/Redis 隔离验证使用测试服务器 `/opt/satori-test/integration/delivery-20260909`，独立容器与网络、不发布端口、不使用站点数据库。AI 和支付供应商使用测试替身，不等于真实供应商压测。本次没有部署到生产或切换测试站点。
