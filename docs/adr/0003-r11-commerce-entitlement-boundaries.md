# ADR-0003：R1.1 商业交易、会员、权益与核销边界

- 状态：Accepted
- 日期：2026-08-28
- 决策范围：R1.1 商品、报价、订单、支付、交付、退款、会员、服务权益、智慧种子与核销

## 背景

R1.0 已有 NestJS 模块化单体、PostgreSQL、Outbox、Worker、幂等和智慧种子总余额账本。R1.1 同时加入真实商品、人民币支付、三档月会员、专项权益包、智慧种子活动价和抽卡前核销。若由页面或具体业务直接操作订单与余额，将无法稳定处理重复回调、交付失败、多来源权益和会员升级。

## 决策

1. 继续采用模块化单体，API 与 Worker 独立部署；不为 R1.1 拆微服务。
2. 模块按 `catalog`、`pricing`、`order`、`payment`、`fulfillment`、`membership`、`entitlement`、`complimentary-seed`、`consumption` 划分。
3. 每个模块拥有自己的领域对象、表和 repository；模块不得直接修改其他模块拥有的表。
4. 人民币购买/会员服务权益与智慧种子使用两套物理、逻辑独立账本，只通过共同端口参与核销候选。
5. 今日能量、抽卡问事等业务只依赖 `ConsumptionPort`，不直接调用账本或计算优先级。
6. 核销优先级固定为会员当期权益、最早到期购买权益包、最早到期智慧种子；用户不能切换。
7. 抽卡前必须预留；30 分钟内未正式抽卡自动释放；抽卡后由生成任务终态提交或释放。
8. 商品、报价和订单快照版本化。报价有效 15 分钟，未支付订单 30 分钟关闭。
9. 支付、订单、交付、退款分别维护状态。支付成功通过事务 Outbox 启动可重放的交付 Saga。
10. 首期仅实现微信支付，但支付渠道必须通过 `PaymentProvider` 接入。
11. 权益包允许重复购买，每次购买形成独立批次，从支付成功当天按 `Asia/Shanghai` 自然日计时。
12. 会员续费排队到当前周期之后；会员权益不结转。
13. 会员升级新订单全额支付，新方案安全生效后终止旧方案；旧周期剩余权益不退款、不抵扣、不结转。剩余价值只作内部分析。
14. 普通订单退款和无法履约异常退回继续使用独立退款流程，不能与会员升级剩余价值混用。
15. 人工调整必须追加流水并记录操作者、原因和关联业务，不允许直接修改余额。

## 模块依赖规则

```text
业务模块 ──> ConsumptionPort
Consumption ──> BenefitSourcePort <── Entitlement / ComplimentarySeed

Order ──> PaymentPort
Payment ──event──> Fulfillment
Fulfillment ──command──> Entitlement / Membership
Membership ──command──> Entitlement
```

- `payment` 不依赖 `entitlement` 或 `membership`。
- `entitlement` 与 `complimentary-seed` 不互相访问表。
- `consumption` 保存决策与意图，但不拥有任何余额。
- 商业模块只保存 opaque `businessContextType/businessContextId`，不得读取问事正文或报告内容。

## 事务与一致性

- 单模块强一致操作使用 PostgreSQL 事务、行锁、唯一约束和只追加流水。
- 跨模块长流程使用 Outbox + Inbox/业务唯一键，按至少一次投递设计。
- 不使用跨模块长数据库事务，不依赖 Redis 锁保证账务正确性。
- 所有命令携带 `Idempotency-Key`；支付渠道事件以 `provider + providerEventId` 去重。
- 对账任务覆盖资金、交付、权益、种子、消费意图和会员周期。

## 结果与取舍

- 优点：保持当前部署简单，同时形成未来可拆分边界；资金和权益可分别审计；新业务无需复制核销逻辑。
- 代价：两套账本与最终一致交付增加实现量；支付后可能短暂显示“权益发放中”。
- 缓解：共享端口测试契约、明确处理中状态、自动重试和日常对账。

## 被否决方案

- 统一钱包：会混淆人民币权益、会员权益与免费种子的法律和退款语义。
- 页面决定核销来源：会造成客户端规则漂移、多端不一致和不可审计。
- R1.1 直接拆微服务：在当前规模下增加分布式事务与运维成本，不能带来相称收益。
- 会员升级按差价支付或退旧订单余额：与已确认的全额新购、旧权益不退规则冲突。
