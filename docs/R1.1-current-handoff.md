# R1.1 当前实现与交接

核验日期：2026-09-05。工作分支：`release/r1.1`。本文取代旧文档中“R1.1 没有后端、只有候选接口”的状态描述。历史原型不作为当前实现事实源。

## 本批修复

| 顺序 | 实现与验收边界 |
| --- | --- |
| 1. 权益闭环 | 抽牌前预留统一权益；报告落库后核销；最终失败释放；相同用户与请求键重放同一抽牌，输入不一致拒绝。支付确认页读取真实权益来源与成本。 |
| 2. 持久化生成 | API 仅建立任务；同一事务记录任务、Outbox 与问事状态。Worker 执行，心跳/尝试编号隔离陈旧执行，维护任务恢复中断。失败重试沿用原牌面，开启新的消费尝试。 |
| 3. 结果与反馈 | 报告先进入内部 SETTLING，再核销转 READY；对账查询真实业务结果，结算失败重试复用已落库正文。反馈落库、校验归属、同一报告重复提交更新同一条。运营直连解释接口拒绝普通消费者绕过权益。 |
| 4. 架构收敛 | 正式问事视图在 `ReadingScreens.tsx`，演示页在 `ReadingPrototypeScreens.tsx`；共用页头，正式路由不依赖 LegacyProfileFlow。删除未装配的另一套问事编排和无调用的候选客户端；保留实际消费规则及测试。 |
| 5. 消费记录收敛 | 用户端 `/me/usage-records` 只返回最终扣费成功的 `COMMIT` 记录；内部预留、释放、到期和调整流水仍保留在只追加账本中，不再作为用户消费记录展示。权益页逐条显示消费服务、扣减权益来源与次数、上海时区日期和时间。 |

## 唯一契约和主要代码入口

- HTTP 契约：`backend/openapi/openapi.yaml`。前端类型由它生成到 `frontend/src/api/contracts/generated.ts`，由 `frontend/src/api/client.ts` 调用。
- 问事接口以 `/api/v1/card-readings` 为前缀：`POST /draws`、列表、详情、`/:readingId/complete`、`/retry`、`/feedback`。创建抽牌要求稳定 `Idempotency-Key`。无需客户端提供价格或决定核销状态。
- 正式业务：`backend/packages/modules/src/card-reading/card-reading.service.ts`。`application/index.ts` 只保留消费要求的纯规则，未再建立一套平行状态机。
- 持久化任务：`generation-task` 模块；恢复：`card-reading-maintenance.worker.ts`；真实结果查询：`consumption/repository-adapter/business-outcome.ts`。
- Schema 增量：`backend/drizzle/0021_bumpy_multiple_man.sql`，扩展问事消费关联与请求摘要；本批未对现有业务数据库执行迁移。
- 正式前端：`ReadingNewScreen` → `ReadingPaymentScreen` → `ReadingFlowScreen` → `ReadingScreens` / `ReadingFeedbackScreen`。缺失草稿、缺失记录、网络错误均显示恢复出口。
- 旧 `/reading/prepare` 与购买后返回统一跳转正式发起页并恢复草稿，不再单独预留消费后回首页。未开始生成的预留到期后，再次确认会重新预留并沿用原牌面。

## 测试证据应如何理解

本批按用户要求在测试服务器 `/opt/satori-test/integration/r11-hardening-20260905` 执行；独立 PostgreSQL/Redis，不连接现有站点业务数据库，不调用真实支付，不在用户本机运行测试。

- `backend/tests/integration/card-reading-lifecycle.test.ts`：真实数据库与 Redis / 实际 Worker，覆盖无权益、重复请求、失败释放、冻结卡牌重试、陈旧任务、报告已保存但结算中断、反馈归属和幂等。Aqua 返回由测试替身提供，因此不代表外部工作流验收。
- `backend/tests/integration/consumption-orchestration.test.ts`：统一消费状态和重复结算检查。
- `backend/tests/e2e/auth-flow.test.ts`：已有真实 HTTP 登录、每日指引与任务恢复回归。
- `frontend/tests/r1.1` 与 `card-reading-aqua-flow.test.mjs`：主要是源码接线/契约检查，不应命名为真实业务 E2E。下单状态判定另有直接行为断言。
- 消费记录收敛在测试服务器通过后端 264 项单元测试、权益账本 6 项数据库集成测试，以及前端契约校验、类型检查、17 项商城页面检查和 53 页静态构建；专项数据库断言确认同一消费仅对用户返回一条成功记录。
- 旧 Playwright 默认配置明确使用 `dev:e2e:prototype`，只证明原型视觉/交互；正常 `dev` 和 `dev:e2e` 默认关闭原型模式。

逐批通过数和提交见 `docs/plans/2026-09-05-r11-hardening.md`；本轮不沿用历史发布证据中的通过数。
