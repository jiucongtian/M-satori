## 工作顺序

1. 先完成并评审本版本 PRD，明确规则、范围与待决策。
2. 再将 PRD 拆解为可独立验收的用户故事，创建 GitHub `feature` Issues，回链需求及验收编号。用户故事采用“作为【角色】，我希望【能力】，以便【价值】”，并附成功、失败和恢复条件。
3. 用户故事范围明确后开始原型设计；每个原型页面/流程回链用户故事，避免先画页面再补需求。

本次交付处于第 1 步，不表示已完成需求拆分、已创建 Issue 或已开始原型。

## PRD 跟随版本

从本版起，产品需求的版本事实源为 `M-satori` 对应 Release 分支的 `docs/PRD`。`M-satoriSrs/docs/PRD` 作为历史产品蓝图参考，不再承载五福荟新版本的唯一需求基线。后续版本在自己的 Release 分支维护 `docs/PRD`，继承时同步更新版本、范围和差异；不得直接覆盖已发布版本的需求事实。

当前目录中的 R1.2 文件仅为需求备忘。创建 `release/wufuhui_r1.2` 后，将其纳入该分支正式 PRD 评审，并在本版保留迁移说明。

Issue 保存负责人、优先级、实施状态、讨论与验收证据；PRD 保存产品规则和需求编号。两者双向关联，不在 Markdown 维护另一套动态问题状态表。
