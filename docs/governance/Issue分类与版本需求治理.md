# GitHub Issue 分类与版本需求治理

生效范围：`wufuhui_r1.1` 及后续五福荟版本。旧版 Issue 保留历史分类，不批量改写。

## 1. 四类标签

每个需求/变更/缺陷 Issue 必须且只能带以下四类中的一个标签。标题或 Project Type 字段不能代替标签。

| 业务类型 | GitHub 实际标签 | 判定 |
| --- | --- | --- |
| feature | `feature` | 新版本规划的能力或用户故事，包括计划内的体验升级 |
| Change Request（CR） | `CR` | 对已确认的版本需求基线追加或调整行为、范围、结构、体验 |
| BUG | `bug` | 原型、本地、开发或测试阶段发现的实际结果偏离确认预期 |
| 线上BUG | `线上BUG` | 正式环境实际发生的缺陷 |

BUG 沿用仓库已有的小写 `bug` 标签，不额外建立大小写别名。`enhancement`、`documentation`、责任域等辅助标签不能替代四类之一。线上BUG不叠加 `bug`；同一问题从测试追踪到正式发生时，在原 Issue 记录生产证据并改为 `线上BUG`，避免重复计数。

CR 与 BUG 以“确认的预期是否改变”区分：本版计划将初见升级为五福荟，以 feature 用户故事管理；版本基线确认后追加品牌范围调整是 CR；已确认应显示五福荟但仍显示旧 Logo 是 BUG；该缺陷已经发生在正式环境则是线上BUG。新加后台开关是 feature；基线确认后调整已确认开关行为是 CR。

发布批次或 Release Gate 属于协调记录，不是第五种业务需求；其中每个实际需求/缺陷仍必须关联四类 Issue。

## 2. 版本与生命周期

- 本版标签：`release:wufuhui_r1.1`；R1.2：`release:wufuhui_r1.2`。使用完整产品版本，不与旧 `release:R1.1` 混用。
- 每条 Issue 具有一个目标交付版本标签；发现版本、影响版本写入正文，尤其线上BUG需区分“发生在哪版”和“修复进哪版”。
- 先查重，再创建；需求 ID、对应 Release 分支 PRD、验收条目与 Issue 双向关联。
- 沿用现有状态：待梳理 → 待开发 → 开发中 → 待测试 → 待验证 → 已关闭。需求尚待产品决定时使用 `status:needs-product`，不能直接进入开发。
- `priority:*`、`area:*`、状态标签独立于类型。优先级按影响决定，不将线上BUG自动等同于 P0。
- 负责人和最终优先级未确认时留待分诊，不虚构分配；进入待开发前补齐负责人、版本和验收，进入待测试前满足既有治理字段要求。

## 3. 各类型最小正文

| 类型 | 必须记录 |
| --- | --- |
| feature | 背景、用户故事、范围/非目标、PRD 与需求 ID、验收、依赖 |
| CR | 原行为/原基线、目标行为、变更原因、影响范围、PRD 差异、验收及待决策 |
| BUG | 环境与发生版本、复现步骤、预期与实际、脱敏证据、影响、回归用例 |
| 线上BUG | BUG 信息，加发生时间、用户/业务影响、生产版本、临时止损、修复和回退方案、生产验证结论 |

创建表单填写 Release 不会自动添加相应标签：提交后必须核对实际类型和版本标签，分诊时检查；本规范不宣称已配置自动强制校验。

## 4. 变更与关闭

PRD 的冻结后变更先建/关联 CR，再同步对应版本文档、原型、契约和验收。修复缺陷不应偷偷改变产品预期；确需改变时关联另一个 CR。拆分 Issue 保留来源及依赖，不把同一交付重复计数。

每个实现 PR/commit 引用 Issue。提交代码不等于验收关闭；关闭记录包含目标分支提交、测试环境版本、回归证据及产品/测试结论。线上BUG还需记录正式环境修复结果。

统计按目标版本和四类分别汇总新增、关闭、未关闭、优先级及阻塞项。PRD 不复制这些实时状态。

## 5. 文档与版本

五福荟 PRD 位于对应 Release 分支 `docs/PRD`；需求来源参考库不替代版本基线。本规则与旧文档的类型字段冲突时，本规则优先。历史版本原有流程不追溯改写。
